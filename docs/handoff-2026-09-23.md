## 1. Screen matching (DONE 2026-09-23, see [session](sessions/2026-09-23-screen-matching.md): per-app scope, threshold 8)
**How it works now.** `CrawlerAgentService._track_screen` calls `ScreenTracker.process_screen` (`domain/screen_tracker.py`) on each decision's screenshot. The hash is a 64-bit dHash (`domain/screen_hash.py`), and a Hamming distance of 12 or less counts as the same screen (`HAMMING_THRESHOLD`). `ScreenRepository.find_similar_screens` loads **every row of `screens`**, from any run and any app, and compares them in Python.

**a) Match only within the same app. Recommended: yes.**
- A match across apps is never meaningful.
- Because matching is global, a blank or loading screen can take the id of another app's screen, and `screens.first_seen_run_id` then points to the wrong app.
- `screens` has no package column. The package can come via `first_seen_run_id` -> `runs.app_package`, or from a new `app_package` column (a migration in `infrastructure/database.py` plus a backfill from `runs`). The column is simpler and cheaper to query.
- This also bounds the full-table scan, which otherwise grows forever.
- Open question: match per app across runs (good for "is this screen new to this app?", which `prompt_builder` novelty signals may want), or per run? Suggest per app.

**b) Same form, different typed text (run 180: screenshots 2-5 hashed within 1-5 bits of each other and got one id).**
- This is correct behaviour, not a bug: it is one screen in different states. dHash on a 9x8 grayscale thumbnail ignores small text changes by design.
- The real problem in run 180 was the agent retyping the password over and over, and loop detection is what catches that. Screen identity should stay coarse.
- Possible concerns in the other direction:
  - Two genuinely different screens with the same layout (onboarding pages that differ only in the question text) may be merged. Run 179 had many such "Next" pages; not measured.
  - Options, if that turns out to matter:
    - Lower the threshold (e.g. 6-8). Cheap, but a scrolled or animated screen then becomes a "new" screen.
    - Add a second signal: the Android activity plus a hash of the a11y tree's structure (element classes and resource ids, not text), once Portal works.
    - Hash the element list instead of pixels.
  - Recommendation: keep dHash plus the per-app scope for now. Check how many distinct screens run 179's ~36 screenshots give at thresholds 12/8/6 (screenshots are in `%APPDATA%/mobile-crawler/output_data/run_179_20260923_124806/screenshots/`). Only add a structural signal when the a11y tree is available.

## 2. Start each run from a clean app state (DONE 2026-09-23, see [session](sessions/2026-09-23-restart-app-before-run.md))
**What the user wants.** A setting, **on by default**, that force-stops the target app before the run so every run starts from the launcher screen. It needs a GUI checkbox and a CLI flag. When it is off, keep today's behaviour.

**Today.** `CrawlerAgentService._ensure_target_app_active_before_crawler` (around line 461) returns early if the target app is already in the foreground. Otherwise it runs `ADBActionExecutor.am_start_recovery`. Nothing force-stops the app, so a run resumes wherever the last one left off.

**Plan.**
- Add a config key (e.g. `restart_app_before_run`, default True) in `config/defaults.py`.
- When the key is on: call `ADBActionExecutor.force_stop_package(app_package)` (`domain/adb_action_executor.py:775`), then launch as now. Do not return early when the app is already active.
- GUI: add a checkbox in the Settings panel, near the crawl limits (`ui/widgets/settings_panel.py`).
- CLI: add `--restart-app/--no-restart-app` as a single-run override via `ConfigManager.override()`, like `--parser-mode`. Do not persist it, and keep it consistent with the #25 discussion.
- Include the key in the config snapshot (`domain/run_config_snapshot.py`).
- Note: force-stop keeps the app's data, so a logged-in or half-finished sign-up state survives, but the app restarts at its launch screen. Wiping data (`pm clear`) would be a different, destructive option; ask before adding it.
- Tests: service test that force-stop is called before launch when the key is on and skipped when it is off; CLI flag test; settings round-trip.

## 3. Better Portal instructions (GUI and CLI) (DONE 2026-09-23, see [session](sessions/2026-09-23-portal-instructions.md))
The user's screenshots of the Portal app show **"Socket Status: Service not available"**, an IP and token under Network Access, an "ADB Forward Command: `adb forward tcp:8080 tcp:8080`", and an Endpoints section. The user thinks there are two ways to connect: an API key, or IP + token.

**What the crawler actually uses.**
- `tools/android/portal_client.py` talks to Portal over **adb**: the content provider `content://com.mobilerun.portal/...`, with optional TCP through an adb port forward, where the auth token is fetched automatically through the content provider.
- It never needs the user to copy the IP, token or API key. Those are for Portal's own remote and cloud access.
- The only thing missing is the **accessibility service being on**. "Service not available" in the app means exactly that.
- Verify these points in the new session before writing the text. In particular, check what the API-key option in the Portal app is (probably Mobilerun cloud) and say so in the instructions.

**Plan.**
- Improve `core/pre_run_warnings.py::_portal_warning` and the Settings panel's Portal status/help text (`ui/widgets/settings_panel.py` around line 600, "Install / enable Portal") with numbered steps for a Samsung/Android 15 phone:
  1. Settings > Accessibility > Installed apps (on Samsung: "Installed apps"; on stock Android: "Downloaded apps") > Mobilerun Portal > turn on, then allow.
  2. If the toggle is greyed out (Android 13+ "restricted setting" for side-loaded APKs): App info > Mobilerun Portal > ⋮ > "Allow restricted settings", then retry step 1.
  3. Samsung may turn the service off after an update or battery optimisation; set the Portal app's battery use to "Unrestricted".
  4. Check: Portal app shows the socket/service as available, or run `crawl` again (the warning disappears). Settings' "Check Portal" button does the same.
  5. The IP / token / API key in the Portal app are **not needed** for this crawler.
- Also consider an **auto-fix**: `portal.enable_portal_accessibility` (`settings put secure enabled_accessibility_services ...`) already exists and is what "Install / enable Portal" runs. The pre-run warning could offer it (GUI: an "Enable now" button in the dialog; CLI: suggest a command or add `--enable-portal`). On Samsung, writing the secure setting over adb usually works without root; test it on the phone.
- The CLI has no Portal commands yet. Consider `portal status` / `portal enable` subcommands that reuse `ui/portal_actions.py` (move that module out of `ui/`, since it is Qt-free).
